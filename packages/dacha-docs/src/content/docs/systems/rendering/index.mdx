`Renderer` draws the actors of the active scene. It is built on
[pixi.js](https://pixijs.com/) 8 and draws with WebGL.

An actor is drawn when it has a **view component**. The renderer creates a pixi.js object for each
view component and places it at the actor's position.

| Component | What it draws | See |
| --- | --- | --- |
| `Sprite` | An image, a frame from a sprite sheet, or a tiled image | [Components](/systems/rendering/components/) |
| `Shape` | A rectangle, circle, ellipse or line | [Components](/systems/rendering/components/) |
| `BitmapText` | Text with a bitmap font | [Components](/systems/rendering/components/) |
| `PixiView` | Any pixi.js object you create in code | [Components](/systems/rendering/components/) |
| `Mesh` | An image with your own shader | [Shaders](/systems/rendering/shaders/) |

## Setting it up

The [starter project](/getting-started/installation/) includes `Renderer`, `CameraSystem` and
`Sprite`. Add the other view components you use to the engine's `components` array:

```ts
import { Engine, Renderer, CameraSystem, Transform, Sprite, Shape, BitmapText } from 'dacha';

const engine = new Engine({
  config,
  systems: [Renderer, CameraSystem, ...gameSystems],
  components: [Transform, Sprite, Shape, BitmapText, ...gameComponents],
  assets: [],
});
```

`Renderer` has three options:

| Option | What it does |
| --- | --- |
| `windowNodeId` | The id of the element the renderer adds its canvas to. The canvas takes the size of this element |
| `backgroundColor` | The colour behind everything. It can be transparent |
| `filterEffects` | Post-processing for the whole screen. See [Filter effects](/systems/rendering/filter-effects/) |

If the element with `windowNodeId` does not exist, the renderer throws when the engine creates it.

### Order in the systems list

`Renderer` needs `CameraSystem`, and `CameraSystem` must come before it in the systems list.
Otherwise the renderer throws when the engine creates it. See [Camera](/systems/camera/).

Put `Renderer` after every system that moves actors or changes their view components. The
renderer draws in `update`, and it draws the state it finds at that moment. A change made by a
system below it appears one frame later.

## How an actor is drawn

The renderer places each view at the actor's `Transform`. Position, rotation and scale all
apply. The view is centred on the actor's position.

An actor can have several view components, one of each kind. For example, a `Sprite` for the
body and a `BitmapText` for a name above it.

A child actor moves, rotates and scales with its parent, as its `Transform` says.

The renderer reads the view components in every `update`. Change a field, such as `opacity` or
`color`, and the next frame shows the change.

If the actor has an [`Interpolation`](/systems/interpolation/) component, the renderer draws it at
the smoothed position instead of its `Transform`.

## Draw order

Two settings decide what is drawn in front: the **sorting layer** of each view, and the **sorting
order** inside a layer. You find both under *Sorting* in the editor's Project settings tab. They
are the `sorting` entry in [global options](/concepts/configuration/).

The actor hierarchy does not affect draw order. A child actor is not drawn above its parent
unless the sorting settings put it there.

### Sorting layers

Every view component has a `sortingLayer` field with the name of a layer. The layers are drawn in
the order of the list. The first layer is at the back, and the last layer is in front.

The starter project has two layers, `background` and `default`. A new view component uses
`default`.

A view whose `sortingLayer` names a layer that is not in the list is drawn behind all layers, with
no sorting.

The renderer creates the layers when the game starts. So adding, removing or reordering a layer
needs a restart. The editor shows *Reload Required* when you change the list. You can move a view
to another existing layer at runtime by changing its `sortingLayer`.

### Sorting inside a layer

Inside a layer, the renderer sorts views by position in every frame. It compares `y` first, then
`x` when `y` is equal. The `order` setting says which views are drawn in front:

| Order | Drawn in front |
| --- | --- |
| `bottomRight` | Lower views. At the same height, views further right |
| `bottomLeft` | Lower views. At the same height, views further left |
| `topLeft` | Higher views. At the same height, views further left |
| `topRight` | Higher views. At the same height, views further right |

`bottomRight` is the default. It suits a top-down game: a character in front of a tree is lower on
the screen, so it is drawn over the tree.

The renderer sorts by the centre of the view. For a tall sprite, the centre is not where the
object touches the ground. Use `sortOffset` to move the point the renderer sorts by. For example,
a tree 64 pixels tall stands on the ground at its bottom edge, so give it a `sortOffset` of
`{ x: 0, y: 32 }`.

## Loading images and fonts

The renderer loads images and fonts by path. It does not use the engine's asset registry.

When a scene loads, the renderer collects every path from two places:

- the `Sprite`, `Mesh` and `BitmapText` components of the actors in that scene,
- the same components in all templates of the project.

The scene becomes active only after these files have loaded. So an actor you spawn from a template
is drawn with its image from the first frame.

A path that appears in neither place is not loaded in advance:

- An actor you create in code with a new path loads its image in the background. Until the image
  arrives, the sprite is drawn as a white rectangle.
- If you change `src` of an existing sprite to a path that was never loaded, nothing changes. The
  sprite keeps its previous image.

To switch a sprite to another image at runtime, put that image on an actor or a template.

The renderer samples all textures with the nearest pixel, with no smoothing. Pixel art stays
sharp when you scale it. Smooth artwork looks pixelated when it is drawn larger than its size.

## RendererAPI

Get `RendererAPI` from the world:

```ts
import { RendererAPI } from 'dacha';

const renderer = world.systemApi.get(RendererAPI);
```

| Method | What it does |
| --- | --- |
| `intersectsWithPoint(x, y)` | Returns the actors whose views contain the point, the one drawn in front first |
| `intersectsWithRectangle(minX, minY, maxX, maxY)` | Returns the actors whose view centres are inside the rectangle |
| `getBounds(actor)` | Returns the rectangle that contains all views of the actor, or `null` if it has none |
| `getRenderingContext()` | Returns the pixi.js `Application` |
| `addFilterEffect`, `removeFilterEffect`, `clearFilterEffects`, `getFilterEffects` | Change filter effects at runtime. See [Filter effects](/systems/rendering/filter-effects/) |

All coordinates are world coordinates.

`intersectsWithPoint` and `getBounds` use the axis-aligned rectangle around each view, not its
exact shape. A click on a transparent corner of a sprite still hits it.

### Finding the actor under the pointer

`MouseControl` events carry the pointer position in world coordinates. Pass it to
`intersectsWithPoint`:

```ts
import { RendererAPI } from 'dacha';
import type { MouseControlEvent } from 'dacha/events';

private handleClick = (event: MouseControlEvent): void => {
  const renderer = this.world.systemApi.get(RendererAPI);
  const [topActor] = renderer.intersectsWithPoint(event.x, event.y);

  if (topActor) {
    // the player clicked topActor
  }
};
```

The `dacha/renderer` subpath exports TypeScript types only, such as `SortingLayer`, `Sorting` and
`Bounds`. Import classes and values from `dacha`.
